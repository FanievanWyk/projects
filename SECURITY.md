# Public Disclosure & Security Checklist

This portfolio is intended to demonstrate professional capability without exposing information that could create security, privacy, contractual, or reputational risk.

## Never publish

- Organisation, learner, employee, customer, or supplier personal information
- Passwords, secrets, API keys, certificates, tokens, or recovery codes
- Public or private IP addresses, domains, hostnames, VLAN IDs, firewall rules, ports, VPN details, or network diagrams that identify a live environment
- Security weaknesses, unresolved incidents, unsupported systems, or exploitable design details
- Serial numbers, asset tags, licence keys, invoices, quotations, budgets, or contract terms
- Screenshots containing names, email addresses, browser tabs, tenant details, device IDs, or internal URLs
- Configuration exports, database extracts, logs, or backups
- Information owned by an employer, client, vendor, or third party without written permission

## Safe presentation rules

- Describe the organisation generically.
- Round scale figures where exact numbers are unnecessary.
- Explain the problem-solving method rather than exposing the production configuration.
- Use diagrams recreated from scratch with fictional names and non-routable example addresses.
- Describe vendors only when they demonstrate a relevant skill and do not reveal sensitive architecture.
- State clearly when a diagram, configuration, or dataset is illustrative.
- Remove metadata from images and documents.
- Review every file and commit before changing the repository to public.

## Final approval gate

The repository must remain private until:

- Every file has been reviewed for sensitive data.
- All claims can be supported in an interview.
- Employer-owned material has been removed or recreated.
- Links work and wording is professionally proofread.
- Fanie has explicitly approved public release.
